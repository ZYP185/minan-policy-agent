# 民安 · 社区民生政策服务智能体

让居民不用知道政策叫什么名字，说说自己的情况，就能知道**能领什么钱、够不够条件、要带什么、去哪办**。

---

## 快速开始

```bash
# 1. 配置 API Key（二选一）
set DEEPSEEK_API_KEY=sk-xxxxxx
#    或复用已有的 ANTHROPIC_AUTH_TOKEN

# 2. 启动
python run.py
```

浏览器会自动打开 `http://127.0.0.1:8848/`。

**零第三方依赖**——只用 Python 标准库，不需要 `pip install` 任何东西。

### 语料还没构建时

```bash
python -m ingest.build --urls urls.txt --structure   # 抓取 + 结构化
python -m ingest.build --selftest                    # 离线自检，不联网
```

## 为什么这不是一个"政策版 RAG 问答机器人"

普通 RAG 的链路是「检索 → 生成」，模型看到几段政策文本就自由发挥。这在民生场景是危险的：
**给错补贴信息，居民会白跑一趟，甚至错过申报期。**

本项目的区别在于：**事实由代码确定，推理由模型负责。**

| 环节 | 普通 RAG | 民安 |
|---|---|---|
| 居民问"我家老人能领什么" | 直接生成一段回答 | 先 `update_profile` 记录，追问 2-3 个关键问题，再 `assess_eligibility` |
| 判断是否符合条件 | 模型"读"政策后自己判断 | **规则引擎**按 `eligibility_rules` 逐条比对，返回确定性结论 |
| 材料清单 | 模型从原文摘抄，可能漏项 | `check_materials` 与居民已有材料做集合比对，列出缺哪项 |
| 检索不到相关条款 | 用常识补一个像样的答案 | 明确说"没找到，建议拨打 12345" |
| 政策时效 | 不知道 | 每条政策带生效/失效日期，检索时自动过滤已废止 |

### 八个工具构成的能力闭环

| 工具 | 作用 |
|---|---|
| `update_profile` | 记录居民画像槽位 |
| `search_policy` | BM25 + 地域/时效过滤 + LLM 重排 |
| `read_clause` | 读条款完整原文（引用前必读） |
| `assess_eligibility` | **政策体检**：规则引擎逐条比对，给出符合度 |
| `check_materials` | 材料清单核对 |
| `get_process` | 办理流程 / 地点 / 时限 |
| `generate_form` | 按画像预填申请表草稿 |
| `scan_unapplied` | 【社区端】辖区政策覆盖扫描 |

### 检索为什么要三级

居民说"我失业了没钱花"，政策写"处于法定劳动年龄内、有劳动能力且处于无业状态的人员"。
字面完全不重叠，纯向量检索也未必能跨越这个鸿沟。所以：

1. **BM25 初筛**（捞得全）—— 中文用字符 bigram，政策术语（"最低生活保障""灵活就业"）是高频固定搭配，bigram 天然能捕捉
2. **元数据过滤**（政治正确）—— 只能用本地、生效中的政策。同一件事在 A 区和 B 区答案不同，国家级和区级也可能不同
3. **LLM 重排**（排得准）—— 让模型理解"失业了"约等于"无业状态"，重排前 12 条

### 结构化抽取是地基

`ingest/structure.py` 把政策原文里的自然语言条件翻译成机器可判定的规则：

```
"本办法适用于具有本市户籍且年满80周岁的老年人"
        ↓
[{"field": "hukou", "op": "eq",  "value": "本市户籍", "desc": "具有本市户籍"},
 {"field": "age",   "op": "gte", "value": 80,        "desc": "年满80周岁"}]
```

有了这层，`assess_eligibility` 才能给出**确定性**结论。同时提示词明确要求把
"80-89 岁每月 180 元 / 90-99 岁每月 350 元"这类**待遇分档**放进 `benefit`，
而不是误当成准入条件——这个区分是体检准确与否的关键。

## 扩库与更新

政策库不是一次建成的。系统提供三个能力应对"库不够用"和"库会过期"。

### 一、覆盖自知 —— 先知道自己缺什么

居民提到某个城市，Agent 会先调 `check_coverage(region)`，
确定性地判断库里有没有该地区的地方政策。

```python
check_coverage("上海市")  → covered=True，本地 7 份，全国性 16 份
check_coverage("广州市")  → covered=False ← 此时禁止拿其他城市的标准作答
```

**为什么这个最要紧**：拿上海的 180 元标准回答广州居民，是这类系统最危险的
失败模式——居民照着办会白跑一趟。没有这个检查时，模型可能"顺手"引用
检索到的外地政策；有了它，缺覆盖会被硬性拦下。

### 二、自动扩库 —— 补上缺的地区

给一个城市政策栏目的入口页，自动发现并入库：

```bash
# 先看能发现什么（不写入）
python -m ingest.expand --entry <入口URL> --pages 3 --dry-run

# 只收民生类，全部入库
python -m ingest.expand --entry <入口URL> --pages 3 --livelihood --yes

# 自己挑编号
python -m ingest.expand --entry <入口URL> --pick 1,3,5
```

发现逻辑**不依赖站点适配器**，只靠两条通用规则：
1. 链接文本含政策特征词（办法/细则/通知/意见/方案…）且不含噪声词（解读/更多/打印…）
2. **试抓验证**——真正抓下来看正文汉字数和条款数，不是政策正文的丢掉

实测：西安市政策文件库 6 页共发现 20 个候选，验证全部为真政策正文
（条款 26-62 条，结构完整）；`--livelihood` 能在标题层面滤掉数据管理、
交通管制、应急预案这类非民生文件。

**能力边界（实测，不是推测）**：

| 站点类型 | 表现 |
|---|---|
| 静态列表页（西安、部分区县政务公开平台） | ✅ 效果好 |
| JS 动态加载列表页（杭州规范性文件库、重庆、武汉`?channelid=`） | ❌ 发现不到，需人工换入口 |
| 反爬 / 证书异常（成都 412、深圳 SSL） | ❌ 抓不到 |
| 城市级政策 | **gov.cn 帮不上忙**——实测其政策库 249 条结果全是国家级，不收地方政策 |

所以这是**半自动**扩库：机器负责发现和验证，人负责提供入口和确认。
人工确认是刻意保留的——自动发现的标题里难免混进解读稿、废止公告；
收错一条，居民就会被误导一次。

### 三、增量更新 —— 让库不过期

```bash
python -m ingest.refresh --check      # 只巡检，不改动
python -m ingest.refresh              # 巡检并更新变更内容
python -m ingest.refresh --re-structure
```

对每条政策：重抓原文 → 比对正文指纹 → 检查失效日期。输出五类结果：

| 结果 | 含义 | 处理 |
|---|---|---|
| 未变更 | 指纹一致 | 无 |
| **内容有变更** | 政策被修订过 | 更新正文，删除旧的结构化结果以便重做 |
| **已过有效期** | 超过失效日期 | 标记 `_stale`，检索时排除 |
| 抓不到了 | 网站改版或页面下线 | 人工确认新地址，或删除 |
| 无法复核 | 没记录原始 URL | 人工补 URL |

指纹做了归一化（去空白、去全角空格），所以**换行和空格的抖动不会误报**，
只有真实内容变更才会触发。

**一条过期的政策比没有政策更糟**：没有数据时系统会说"我不知道"，
有过期数据时它会自信地给出错误答案。

## 自检

```bash
python tests/run_all.py              # 全部检查
python tests/run_all.py --offline    # 只跑不需要联网的（约 2.5 秒）
```

分项：

```bash
python tests/test_core.py            # 分词 / BM25 / 金额抽取，不联网
python tests/test_parse.py           # HTML 解析 / 元数据 / 条款切分，不联网
python tests/check_frontend.py       # JS 语法 / id 引用 / 卡片渲染器，不联网
python tests/test_server.py          # 认证闸门 / 请求体加固 / 会话收尾，不联网
python -m ingest.build --selftest    # 全链路：解析→入库→检索→规则引擎，不联网
python tests/test_retrieval_real.py  # 检索质量（真实语料）
python tests/test_agent.py           # Agent 端到端（会真实调用模型）
```

> `test_agent.py` 是拿真实模型跑固定剧本的冒烟测试，模型的随机性会让
> 它偶尔失败（比如该做体检的那轮选择了先反问城市）。**失败时先重跑一次**
> 再判断，别急着改代码。抗幻觉那条通常是稳的。

`test_agent.py` 里有一条**抗幻觉测试**：居民问"听说养狗每月发 500 元宠物补贴"，
库中并无此政策，Agent 必须承认查不到，而不是编一个像样的答案。

### 实测检索质量

10 条居民口语提问（如"我失业了有什么补助""赡养老人有什么支持政策"）打在
98 份真实政策上：

| 指标 | 仅 BM25 | BM25 + LLM 重排 |
|---|---|---|
| 召回率（前 5 名内命中期望政策） | 10/10 | 10/10 |
| Top1 命中 | 5/10 | **8/10** |
| MRR | 0.720 | **0.900** |

这个数字背后有一次实测驱动的修复，值得记下来：

**候选池不能按返回条数截断。** 原实现里 `top_k` 同时当"候选池大小"和
"最终返回条数"，于是重排只能看到 BM25 的前 5 名。测试时发现，
问「生孩子有什么补贴可以领」，正确的《育儿补贴制度管理规范》
BM25 只排到**第 7**——因为"生孩子"和"育儿"没有任何共同字符 bigram，
字面只共享"补贴"两个字。它进不了候选池，重排也就无从救起。

把候选池改为独立的 `TOP_K_RETRIEVE`（默认 12）后，MRR 从 0.833 提到 0.900。
这个 bug 影响的是**所有**查询，不只是生育类。

诚实说明样本量：只有 10 条查询，这个数字作趋势参考，不构成统计结论。
重排的价值集中在语义跨度大的提问——「赡养老人有什么支持政策」，
BM25 把《保障性租赁住房意见》排到第一，重排纠正为《推进互助性养老
服务发展的意见》。

### 类别覆盖

按 8 个民生类别各问一个典型问题，看能否答上（判定标准是命中政策的
**类别标记正确**，不用关键词子串匹配——那样会因发文机关含"教育部"
三字把养老政策误判为命中，反而盖住真实缺口）：

```
养老 #1   救助 #1   医疗 #1   住房 #1
生育 #1   就业 #2   残疾人 #3  教育 #1
```

8/8 可答。但已知两个数据质量问题，尚未修正：
- 部分政策的类别标记有误（如《…加快推进养老服务…》因首位发文机关是
  "教育部"被标成「教育」）
- 有 2 份政策未分类

类别字段不参与主检索过滤，所以不影响问答准确率，但会让覆盖报告失真。

## 设计取舍

**为什么不用向量数据库？**
演示环境要求零依赖。BM25 + LLM 重排在中文政策语料上召回质量足够，
且省掉了嵌入模型下载和向量库部署。要升级的话，`retriever.py` 的 `search()`
是唯一改动点，加一路向量召回做混合检索即可。

**为什么前端手写而不用框架？**
`web/index.html` 是单文件，无构建步骤。答辩时拷到任何装了 Python 的电脑上
双击 `run.py` 就能跑，不会出现"环境装不上"的尴尬。

**为什么颜色只用于状态？**
政策类别等分类信息一律用中性色 + 文字。颜色承担两种以上语义时，
使用者就无法判断"这个蓝色到底代表什么"。状态色（符合/可能符合/不符合）
永远以「图标 + 文字 + 颜色」三重编码出现，色盲用户和黑白打印都不丢信息。

## 部署

线上版本带登录页，评委凭账号密码访问。完整步骤见 **[DEPLOY.md](DEPLOY.md)**。

一句话说清设计：**绑定回环地址时不启用登录**（本地双击 `run.py` 的体验不变），
**绑定对外地址时强制登录**（未设账号密码直接拒绝启动）。因为一旦对外，
没有认证就等于把 API Key 交给了整个互联网。
